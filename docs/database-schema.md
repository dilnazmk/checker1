# CheckMate — Database Schema Specification

**DBMS:** PostgreSQL 16 · **ORM:** Prisma · **Diagram:** [`docs/erd.pdf`](./erd.pdf) (Crow's Foot notation)

---

## 1. Overview

CheckMate stores users (students and teachers), teacher-owned groups, assignments with weighted rubrics, student attempts, AI review drafts, per-criterion scores and an audit log of attempt state changes. The model has **12 tables**:

| Domain | Tables |
|---|---|
| Identity & access | `users`, `sessions`, `password_resets` |
| Groups | `groups`, `group_members` (junction) |
| Assignments & rubrics | `assignments`, `assignment_groups` (junction), `criteria` |
| Attempts & review | `attempts`, `ai_reviews`, `criterion_scores`, `attempt_events` |

Conventions: all primary keys are `UUID` generated by the application; all timestamps are `TIMESTAMPTZ` (stored in UTC); table and column names are `snake_case`.

## 3. Relationships and Cardinality

| # | Parent → Child | Cardinality | FK | ON DELETE | Business rule |
|---|---|---|---|---|---|
| R1 | users → sessions | 1:N | sessions.user_id | CASCADE | A session has no meaning without its user. |
| R2 | users → password_resets | 1:N | password_resets.user_id | CASCADE | Reset tokens belong to one account and expire with it. |
| R3 | users (teacher) → groups | 1:N | groups.teacher_id | RESTRICT | A teacher who still owns groups cannot be deleted; groups must be reassigned first. |
| R4 | users (student) ↔ groups | **N:M** via `group_members` | group_members.student_id, group_members.group_id | CASCADE (both) | A student can be in several groups and a group has many students. Removing a group or user removes only the membership row. |
| R5 | users (teacher) → assignments | 1:N | assignments.teacher_id | RESTRICT | Assignments are course records and must keep their author. |
| R6 | assignments ↔ groups | **N:M** via `assignment_groups` | assignment_groups.assignment_id, assignment_groups.group_id | CASCADE (both) | One assignment can be published to several groups; a group receives many assignments. |
| R7 | assignments → criteria | 1:N | criteria.assignment_id | CASCADE | The rubric is part of the assignment. Deleting a draft assignment deletes its rubric. |
| R8 | assignments → attempts | 1:N | attempts.assignment_id | RESTRICT | An assignment that has submissions cannot be deleted — it must be CLOSED instead. |
| R9 | users (student) → attempts | 1:N | attempts.student_id | RESTRICT | Submissions and grades are academic records and must not disappear with an account. |
| R10 | attempts → ai_reviews | **1:1** (0..1) | ai_reviews.attempt_id (UNIQUE) | CASCADE | Each attempt has at most one AI review; the review only exists for its attempt. |
| R11 | attempts → criterion_scores | 1:N | criterion_scores.attempt_id | CASCADE | Scores are part of the attempt. |
| R12 | criteria → criterion_scores | 1:N | criterion_scores.criterion_id | RESTRICT | A criterion that has already been used to score work cannot be removed, otherwise past grades lose their meaning. |
| R13 | attempts → attempt_events | 1:N | attempt_events.attempt_id | CASCADE | The audit log describes one attempt. |
| R14 | users (actor) → attempt_events | 0..1:N | attempt_events.actor_id (nullable) | SET NULL | History is preserved even if the teacher's account is removed. |

Business rules enforced in the service layer (not expressible as simple FKs): a `criterion_scores.criterion_id` must belong to the same assignment as its attempt; `attempt_number` must not exceed `assignments.max_attempts`; submissions are rejected after `deadline`; only users with role TEACHER can own groups and assignments.

## 4. CHECK Constraints (added to the migration)

Prisma does not support `CHECK` in `schema.prisma`, so they are appended to the generated migration SQL (`npx prisma migrate dev --create-only`, then edit `migration.sql`):

```sql
ALTER TABLE "assignments"      ADD CONSTRAINT "assignments_max_attempts_check"   CHECK ("max_attempts" > 0);
ALTER TABLE "criteria"         ADD CONSTRAINT "criteria_weight_check"            CHECK ("weight" > 0);
ALTER TABLE "criteria"         ADD CONSTRAINT "criteria_max_points_check"        CHECK ("max_points" > 0);
ALTER TABLE "attempts"         ADD CONSTRAINT "attempts_attempt_number_check"    CHECK ("attempt_number" > 0);
ALTER TABLE "attempts"         ADD CONSTRAINT "attempts_file_size_check"         CHECK ("file_size_bytes" BETWEEN 1 AND 10485760);
ALTER TABLE "attempts"         ADD CONSTRAINT "attempts_final_grade_check"       CHECK ("final_grade" IS NULL OR "final_grade" BETWEEN 0 AND 100);
ALTER TABLE "ai_reviews"       ADD CONSTRAINT "ai_reviews_likelihood_check"      CHECK ("writing_likelihood" IS NULL OR "writing_likelihood" BETWEEN 0 AND 1);
ALTER TABLE "ai_reviews"       ADD CONSTRAINT "ai_reviews_retry_count_check"     CHECK ("retry_count" BETWEEN 0 AND 3);
ALTER TABLE "criterion_scores" ADD CONSTRAINT "criterion_scores_ai_points_check" CHECK ("ai_points" IS NULL OR "ai_points" >= 0);
ALTER TABLE "criterion_scores" ADD CONSTRAINT "criterion_scores_teacher_points_check" CHECK ("teacher_points" IS NULL OR "teacher_points" >= 0);
```

## 5. Architectural Justification

### 5.1 Query alignment

The schema is shaped around CheckMate's most frequent operations:

- **Student dashboard (FR-04)** — "show my attempts for each assignment": a single lookup on `attempts` by `student_id`, served by the unique index `(student_id, assignment_id, attempt_number)`, joined 1:1 to `ai_reviews`.
- **Submitting an attempt (FR-02, FR-08)** — one transaction inserts an `attempts` row (status QUEUED), an `ai_reviews` row (PENDING) and the first `attempt_events` row; the API returns immediately and the pg-boss worker picks up the job. The unique `(student_id, assignment_id, attempt_number)` makes double submission of the same attempt number impossible even under concurrent requests.
- **Teacher review queue (FR-09)** — `attempts WHERE status = 'REVIEWED' ORDER BY submitted_at`, served by `(status, submitted_at)`; the reviewer then loads the attempt's `criterion_scores` (one row per criterion) and edits only `teacher_points`/`teacher_comment`.
- **Group analytics (FR-10)** — "which criteria fail most often": `criterion_scores` grouped by `criterion_id` with `AVG(teacher_points / max_points)`. Keeping scores as rows (not columns) makes this a simple `GROUP BY`.
- **Separation of AI and human judgement** — `ai_points` and `teacher_points` are separate columns, and `final_grade` lives only on `attempts`, so automated output can never be confused with the teacher's decision (core principle of the project).

### 5.2 Normalization to 3NF

- **1NF:** every column is atomic. Rubric scores are not stored as `score1, score2, …` columns or a JSON list inside `attempts`; each criterion score is its own row in `criterion_scores`. Group membership is not stored as an array of student IDs in `groups` but as rows in `group_members`.
- **2NF:** the only composite keys are in the junction tables (`group_members`, `assignment_groups`); their non-key columns (`joined_at`, `published_at`) describe the pair, not one half of it. Example: `group_name` is kept in `groups`, not in `group_members` — inside the junction table it would depend only on `group_id` (one part of the composite key), which is a partial dependency.
- **3NF:** no non-key column depends on another non-key column. Example: `attempts` does not store `teacher_id` or `group_name` — both are reachable via `assignment_id → assignments.teacher_id` and `assignment_groups`; storing them would create the transitive dependency `attempt.id → assignment_id → teacher_id`. Likewise, the AI total score is not stored in `ai_reviews` because it is computable from `criterion_scores.ai_points`.
- **Conscious decisions:**
  - `users.role` is initially derived from the email format (FR-01). It is stored because it is an authorization fact that must be checked on every request and may later be changed independently of the email (e.g. a teaching assistant), so `email` does not functionally determine `role` in the long term.
  - `attempts.final_grade` is **not** derived from `criterion_scores`: it is the teacher's independent final decision (the teacher may apply a late penalty or override the rubric total), so it is a separate fact, not a computed value.

### 5.3 Cascading rules

The rule for each FK follows one principle: **composition data is cascaded, academic records are protected, audit history is preserved.**

- **CASCADE** — for data that is part of its parent and meaningless alone: `criteria` of an assignment, `ai_reviews`, `criterion_scores` and `attempt_events` of an attempt, junction rows, `sessions` and `password_resets` of a user. Deleting a draft assignment removes its rubric in one statement with no orphans.
- **RESTRICT** — for academic records: a student or assignment with `attempts` cannot be deleted, and a criterion that already has `criterion_scores` cannot be removed. Deleting a user therefore never silently erases submission history or grades; such accounts are deactivated or assignments are CLOSED instead.
- **SET NULL** — for `attempt_events.actor_id`: if a teacher account is removed, the audit trail stays intact and the event simply shows no actor.

### 5.4 Index strategy (B-Tree)

PostgreSQL does not create indexes on foreign keys automatically, so every FK used in joins or filters is indexed:

| Index | Serves |
|---|---|
| `attempts (student_id, assignment_id, attempt_number)` UNIQUE | Student attempt history (FR-04), next attempt number, attempt-limit check |
| `attempts (assignment_id)` | Teacher view of all submissions for an assignment (FR-06) |
| `attempts (status, submitted_at)` | Review queue and worker polling, oldest first (FR-08, FR-09) |
| `ai_reviews (attempt_id)` UNIQUE | 1:1 join attempt → AI review |
| `criterion_scores (attempt_id, criterion_id)` UNIQUE | Loading the rubric scores of one attempt |
| `criterion_scores (criterion_id)` | Analytics: most frequently failed criteria (FR-10) |
| `group_members (group_id, student_id)` PK + `(student_id)` | Group roster and "groups of a student" |
| `assignment_groups (assignment_id, group_id)` PK + `(group_id)` | "Assignments published to my group" |
| `groups (teacher_id, name)` UNIQUE | Teacher's groups; unique names per teacher |
| `assignments (teacher_id)`, `assignments (status, deadline)` | Teacher's assignment list; open assignments by deadline |
| `criteria (assignment_id, position)` UNIQUE | Rubric in display order |
| `attempt_events (attempt_id, created_at)`, `(actor_id)` | Attempt timeline; actions of a reviewer |
| `sessions (user_id)`, `sessions (expires_at)`, `password_resets (user_id)` | Logout-all, cleanup of expired sessions |
| `users (email)`, `sessions (token_hash)`, `password_resets (token_hash)` UNIQUE | Login and token lookup |

Composite indexes are ordered with the equality column first so that one index also serves queries on its leading column (e.g. `(student_id, …)` also serves "all attempts of a student").

### 5.5 Why SQL and not NoSQL

CheckMate's data is highly relational and integrity-critical: grades reference criteria, criteria belong to assignments, assignments are published to groups. A relational database gives:

- **Referential integrity** (FKs, RESTRICT) that protects academic records — in a document store this would be application code only.
- **ACID transactions** for grading: updating `criterion_scores`, `attempts.final_grade` and inserting an `attempt_events` row must succeed or fail together.
- **Analytics with JOIN / GROUP BY** across groups, assignments and criteria (FR-10) without duplicating data into documents.
- **The job queue in the same database:** pg-boss runs on PostgreSQL, so creating an attempt and enqueuing its AI job happen in one transaction.

A NoSQL store would suit the unstructured AI output, but `extracted_text` and `draft_feedback` fit well in `TEXT` columns (and `JSONB` is available if needed), so a second database is not justified.
